# Ultimatrix — End-to-End Audit Findings

**Audit goal:** identify implementation, wiring, logical, prompt, model-routing, context, worker/swarm, memory, and runtime gaps that can inform a more reliable general-purpose SDK foundation.

**Method:** source-level inspection of the uploaded `Ultimatrix-master` repository. These findings are based on executable wiring and prompt/runtime contracts, not README architecture alone. No exploitation skills or attack logic were executed.

## Findings

## Emerging root cause

The strongest pattern is **not** “single-agent good, swarm bad.” The recurring problem is **open-loop intelligence and mismatched runtime contracts**:

- discovery exists, but activation is repeatedly forgotten;
- skills exist, but the bootstrap and context-pressure policy favor generic tool discovery;
- workers exist, but do not inherit the orchestrator’s live capability universe;
- task completion exists, but task success is not always evaluated;
- Reflexion records failure, but its feedback is incompletely reinjected;
- anti-loop instructions exist, but the signal is parsed from the wrong channel with an incompatible regex;
- context protection computes corrections that are not always applied to the live agent;
- model adaptation exists as APIs, but production feedback does not close the loop;
- memory/context tools promise more state than they actually return.

## SDK implication

For the new SDK, every adaptive subsystem should satisfy a strict closed-loop contract:

**Observe → Decide → Apply → Verify → Persist → Rehydrate**

A feature should not count as “wired” merely because its class, registry entry, prompt instruction, or unit test exists. The SDK should have end-to-end contract tests proving that the state change actually reaches the next model step and changes behavior.

### Streaming root cause

The streaming problem is not one UI bug. There are **three different concepts mixed together**:

1. **Internal model stream** — provider reasoning, answer deltas, tool calls.
2. **Runtime event stream** — phases, capability activation, worker lifecycle, evidence, graph changes.
3. **User-facing presentation stream** — progress text, tool cards, safe activity summaries, final answer.

Ultimatrix partially separates these, but then reconnects them in the renderers. Raw reasoning becomes durable Web history, renderers synthesize answers from reasoning, worker execution bypasses the main stream, and finalization is represented twice.

For the SDK, these should be separate contracts. The runtime should produce one ordered, replayable **event log**, while adapters derive CLI/Web views from it. The public-facing stream should never need to infer or manufacture the final answer from transient reasoning.
